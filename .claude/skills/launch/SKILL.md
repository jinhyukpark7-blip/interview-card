# /launch — 기능 하나 출시하기

> 사용자가 `/launch`라고 직접 부를 때만 따라요. 이번에 받은 번호: `$ARGUMENTS` (비어 있으면 1단계에서 골라요)
> 모든 단계에서 **CLAUDE.md 규칙**을 지켜요. PRD.md와 CLAUDE.md가 서로 다르면 멈추고 먼저 물어요.

## 1단계. 기능 고르기
- 번호를 받았으면 그 기능을 골라요. PRD.md에 없는 번호면 멈추고 물어요.
- 번호가 없으면 PRD.md "6. 출시 체크"에서 아직 `[ ]`인 기능 중 **번호가 가장 앞선 것** 하나를 골라요.
- 이미 모두 `[x]`이면 "출시할 기능이 없어요"라고 알리고 끝내요.
- 고른 기능과 그 완료 기준 번호를 사용자에게 한 줄로 알려요.

## 2단계. 이미 만들어졌는지 보기
- app.py · test_app.py에서 그 기능의 코드와 시험이 있는지 찾아봐요.
- **이미 있으면** 새로 만들지 않고 바로 4단계(검사)로 가요.
- **없거나 일부만 있으면** 3단계로 가요.

## 3단계. 만들기 (CLAUDE.md 규칙대로)
- 고치기 전에 **3줄 계획**을 먼저 말해요. (규칙 22)
- 특히 지킬 것:
  - `data/` CSV는 줄 덧붙이기만, questions.csv는 읽기만 (규칙 1~3)
  - `make_sample.py`는 허락 없이 실행하지 않아요 (규칙 4)
  - 화면 문구는 PRD와 글자 하나 다르지 않게, 맨 위 `MSG_...`에 모으기 (규칙 7)
  - 숫자 기준은 맨 위 이름 붙인 값으로 (규칙 8)
  - 읽기 · 입력 검사 · 화면 그리기는 따로 함수로 (규칙 9)
  - test_app.py에 완료 기준 시험 추가, 임시 폴더에서만 (규칙 10~11)
  - PRD에 없거나 "하지 않을 것"에 있는 기능은 만들지 않아요 (규칙 13)
  - 쉬운 한국어 주석, `시작하기.md`도 같이 고치기 (규칙 23~24)
- 내가 먼저 `python -m unittest`를 돌려 통과하는지 봐요.

## 4단계. qa-tester에게 검사받기
- `qa-tester` 직원을 불러 **고른 기능의 완료 기준 번호 전부**와 "기록 그대로"를 검사해 달라고 해요.
- 결과는 번호별 ✅ / ❌ / ❓ 표로 받아요. 이것이 **처음 결과**예요.
- 모두 ✅이면 6단계로 가요.
- ❌나 ❓가 있으면 5단계로 가요.

## 5단계. 고치고 다시 검사 (최대 2번)
- ❌ · ❓ 이유를 보고 고쳐요. 고친 것은 "무엇을 · 왜"로 적어 둬요.
- 다시 `qa-tester` 검사를 받아요.
- 고치고 다시 검사하는 것은 **2번까지만** 해요. 2번 해도 ❌ · ❓가 남으면:
  - **멈추고** 지금까지의 표를 보여 주며 어떻게 할지 사용자에게 물어요.
  - PRD.md에는 완료 표시를 하지 않아요.
- "기록 그대로"가 ❌이면 횟수와 상관없이 **바로 멈추고** 사용자에게 알려요.

## 6단계. 완료 표시
- 모두 ✅일 때만 PRD.md "6. 출시 체크"에서 그 기능의 `[ ]`를 `[x]`로 바꿔요. **그 한 칸 말고는** PRD.md를 고치지 않아요.
- GitHub에는 아무것도 하지 않아요. `git add` · `commit` · `push` · PR 만들기 모두 하지 않아요. (규칙 17)
- 대신 커밋 메시지만 제안해요. 예: `F2 내 답변 적기 출시 — 완료 기준 4개 통과`

## 7단계. 마지막 보고 (쉬운 한국어)
아래 세 부분을 차례로 보여 줘요.

1. **처음 결과** — 4단계에서 처음 받은 표
2. **고친 것** — 5단계에서 고친 것 목록 (없으면 "고친 것 없음")
3. **최종 표**

| 번호 | 처음 | 최종 | 확인한 방법 | 남은 문제 |
|---|---|---|---|---|
| F2-1 | ❌ | ✅ | 시험 + 실제 화면 | |
| 기록 그대로 | ✅ | ✅ | 검사 전후 data/ 비교 | |
